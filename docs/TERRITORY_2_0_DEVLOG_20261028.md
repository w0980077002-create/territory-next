# TERRITORY 2.0 — инженерный этап 28.10.2026: серверный PvE-оркестратор

**Репозиторий:** `w0980077002-create/territory-next`, ветка `main`. **Режим:** исключительно исходный код и CI; staging SQL НЕ развёрнут, публичный HTTP-маршрут НЕ добавлен.

## Что реально реализовано

- `server/staging/territory_v2_pve_execution.sql` — приватная схема авторитетного боя. Статистика героя выбирается из таблицы `pve_class_profiles` по классу/уровню; параметры врага — из `pve_stage_profiles` по текущей главе/волне; правила — из явно активированного `pve_active_rules` и `pve_rulebooks`. Все таблицы закрыты RLS и доступом `service_role`; **по умолчанию нет ни одного профиля, активного правила или разрешённой награды**.
- Начало `begin_pve_execution`: получает только **уже проверенный сервером Telegram ID**, новый battle UUID и криптографический seed, блокирует персонажа, проверяет прогресс/владение, собирает снимок, SHA-256, создаёт одну боевую сессию и сохраняет неизменяемый снимок. Повтор с тем же ID возвращает исходный снимок/seed, а не перегенерирует его.
- `read_pve_execution`: приватный серверный resume по Telegram ID и battle ID; seed и статы **не возвращаются публичному клиенту**.
- `finish_pve_execution`: единая транзакция для записи результата, детерминированного receipt и первого прохождения этапа. Если clear не прошёл, запись результата тоже откатывается. Победа не может пропустить волну; поражение не открывает этап. XP, валюты и предметы **не выдаются**.
- `server/combat/runAuthoritativePve.ts`: настоящий оркестратор, использует `crypto.getRandomValues` и `crypto.randomUUID`, детерминированно рассчитывает PvE только по снимку из БД через `resolvePveEncounter`, SHA-256 трассы и два воспроизводимых receipt UUID; передаёт в БД только результат своего расчёта, не результат браузера. Наружу выдаёт только безопасный ID этапа/боя и результат без seed.
- `scripts/check-v2-authoritative-pve.mjs`: интеграция PGlite + TypeScript. Проверяет отсутствие настроек по умолчанию, валидацию профилей, одну активную сессию, неизменяемость снимка, replay, чужой Telegram ID, атомарный rollback, победу/поражение, независимость игроков, RLS, нулевые изменения экономики. Подключено к `npm run test:v2`.

## Границы и дальнейшие задачи

1. **НЕ** включать API `/start` или `/finish` в публичном Edge до полноценного V2 Telegram-HMAC, серверной rate-limit политики, атомарной операции и проверки готовности staging.
2. Баланс героев, монстров и боевых правил **не выдуман**: ни одна таблица не заполнена релизными значениями. Числа в тесте — только фикстуры, не баланс.
3. До боевого релиза нужны: утверждённая версия баланса, доверенная конфигурация уровня/снаряжения, проверка snapshot после изменения экипировки, сервисные лимиты времени/боёв, управление истёкшими сессиями, серверная выдача XP/лута с единственным receipt и телеграм-бот TERRITORY 2.0.
4. **Запрещено** брать исходники/ассеты/формулы из TERRITORY 1.0. Её GitHub, Supabase, игроки, VIP, валюта и бот не менялись.
5. Шесть утверждённых изображений из `docs/TERRITORY_2_0_CANON/SOURCE_OF_TRUTH_RU.md` и фон главного экрана не менялись. Платежи, облачные покупки и релиз игрокам не включались.

## Приёмка CI

Проверка выполняется автоматически GitHub Actions на `main`: `typecheck`, `test:v2` (включая новый SQL-интеграционный сценарий), сборка с offline endpoint. При падении CI фиксировать ошибку и исправлять код, а не отключать проверку.
